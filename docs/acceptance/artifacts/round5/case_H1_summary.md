# 智谱 ZCode 静默上传代码仓库事件：深度研究报告

## TL;DR / 结论（标明置信度）

智谱（Z.ai）官方 AI 编程桌面应用 ZCode 被开发者 ferstar 逆向分析证实：在用户登录状态下，客户端会静默打包整个工作区——包括完整的 `.git` 历史、Git LFS 资产缓存、reflog 以及全局应用配置——用服务器下发的 RSA 公钥加密后，直接上传至阿里云 OSS（置信度：高，有本地抓包与文件系统证据链支撑，发布于 2026-09 博客并经社区广泛传播）。

**上传了哪些内容**：完整工作区快照，其中约 87% 为 `.git` 目录（包含对象、LFS、reflogs），另有 LFS 资产缓存和全局配置。博主用一个 538 个文件的公开仓库做实验，快照被服务端成功接受（置信度：高，博主本地实验可复现）。

**是否跨境**：证据指向数据上传至阿里云 OSS。博主文章英译版提到海外用户对应的 OSS 区域问题，但本次研究中沙箱创建失败（两次 401 授权错误）、LLM 摘要工具亦不可用，**无法从已获取文本中确证 OSS 具体区域（region）及是否存在跨境传输**。官方声明中未提及存储位置。此点标记为“未确认/信息缺口”（置信度：低）。

**官方如何回应**：Z.ai 于 2026-09-18 17:44 在用户社区发布声明，要点为：(1) 问题源于“代码库索引”功能，用于本地索引、会话检查点恢复与 Repo Wiki；(2) 云端生成 Wiki 页面时“可能”触发仓库数据上传；(3) Wiki 生成后上传数据立即销毁、不存储；(4) 功能在早期上线期间默认开启，部分用户受影响，问题“已修复”；(5) ZCode 将开源并接受第三方审查，全体用户获得一次额外的每周额度重置（置信度：高，官方声明经 IT 之家等媒体报道，博主逐条转述核对）。

**各方冲突核心**：官方称仅 Wiki 生成时“可能”上传且即用即毁；博主逆向显示 3.12.3 版本存在随登录常驻的上传 sidecar，`captureBeforePrompt`（每次提问前）与 `repo-wiki-update` 无条件触发上传，且关闭“优化体验”与“仓库快照索引”开关后仍会打包并尝试直传 OSS；“立即销毁”无法从外部验证，且与“会话检查点云端恢复”功能在逻辑上矛盾（置信度：高，冲突双方原文均已获取）。

## 冲突与不确定 / Conflicts & Uncertainties

**1. 上传范围之争（官方 vs 逆向证据）——直接冲突**
- 官方口径：仅“云端生成 Wiki 页面时可能触发上传仓库数据”，上传目的限于 Repo Wiki 生成。
- 博主审计口径（3.12.3 受影响版本）：是全工作区快照，约 87% 体积为 `.git`；且不止 Wiki 一个触发点——`captureBeforePrompt` 在**每次用户提问之前**都会触发上传，`repo-wiki-update` 无条件触发。两者在范围与频率上严重不一致。
- 不确定项：官方未公布上传的确切字段/文件清单，博主亦只能基于打包逻辑与流量观察推断，双方均无第三方审计。

**2. 用户可控性之争（开关是否有效）——直接冲突**
- 官方声明：未提及任何停止上传的开关（对该维度沉默）。
- 博主证据：关闭“优化体验”和“仓库快照索引”后，客户端**仍会打包并尝试直传 OSS**，即开关形同虚设。
- 补充事实：官方承认功能在早期上线期间**默认开启**，即默认状态即为上传状态，用户知情同意存疑。

**3. “立即销毁、不存储”的可验证性——单方宣称，无法核实**
- 官方宣称 Wiki 生成后数据立即销毁、不存储。
- 博主反驳：(a) 云端行为外部无法验证；(b) 逻辑上与官方宣称的“会话检查点（checkpoint）恢复”功能矛盾——若数据即毁，检查点恢复从云端何来？
- 博主实验：538 文件公开仓库的快照被服务端成功接受，服务端接受行为本身不证明“即毁”。
- 3.14.0 版本审计显示云端 `upload-credential` 接口已下线（返回 404），但这**不能证明**历史上已上传的存量云端快照已被物理删除——博主明确指出此点外部不可验证。

**4. 触发机制描述差异**
- 官方用“可能（may）”描述上传触发；逆向证据表明在 3.12.3 中触发是**无条件的、随登录常驻**的。“可能”与“无条件”之间是显著口径差。

**5. 是否跨境——无法核实**
- 已确认数据上传目标是阿里云 OSS；英译版博客提及海外用户的 OSS 区域问题，但本次检索中该部分正文被截断，且沙箱（两次 401 失败）与 LLM 摘要工具（`SUMMARY_LLM_BASE_URL` 未配置报错）均不可用，未能补全区域细节。
- 官方声明对存储地理位置只字未提。
- 结论：**跨境与否暂无法下结论**，列为最高优先级信息缺口。补证方案：抓取博客完整 78,041 字符正文中 OSS region/endpoint 字段；查 ZCode 官方文档对海外版存储区域的说明。

**6. 修复完整性的分歧**
- 官方：“问题已修复”。
- 博主对 3.14.0 的审计证实上传管线代码已被物理移除、仅保留本地检查点、云端凭证接口返回 404——即**客户端层面的修复属实**；但存量云端数据的删除与否、企业合规责任未决。

## 深度背景

ZCode 是智谱（Z.ai）官方 AI 编程桌面应用，类比 Cursor/Claude Code 类产品。“代码库索引”是此类产品的基础能力（用于上下文检索、会话恢复、文档生成 Repo Wiki）。事件的核心张力在于：AI 编程工具为提供智能服务天然需要读取代码，但**读取（本地索引）与上传（云端传输）之间的边界**必须由明示、可关闭、可验证的机制约束。ZCode 3.12.3 的问题在于三者皆缺：默认开启、开关无效、云级行为不可审计。加密设计（公钥云端下发、私钥云端独占）使用户对自己磁盘上的数据毫无掌控，进一步加剧信任危机。官方以“开源 + 第三方审查”回应可验证性诉求，是此类事件中较为积极的补救路径，但落地前仍属承诺。
